# 产品缺口盘点与改进方案

对照《差旅agent设计思路》（仓库根目录 `差旅agent设计思路.md`）逐条检查当前实现，
列出已经做到的、还差的，以及建议的动手顺序。

盘点日期：2026-08-31。代码基准：分支 `semantic-entrypoint-and-judge`。

**进度**：两条 P0（业务指标层、把成本摊到选择那一刻）和 P1 的上下文数据层都已做完，见下；P1 的授权档位与 P2 各条尚未动工。

**2026-09-01 复盘**：第六节重新审视了这份计划和整个架构，结论是**此前的顺序漏掉了一个前提——系统看不见员工到底订没订**。修订后的顺序见 6.4，第 1 项的落地记录见 6.5。第三节和第五节保留原文作为历史，不再是当前的行动顺序。

## 一、一句话结论

设计文档和项目的重合度很高，**但重合的是"守住边界"那一半，缺的是"产生价值"那一半**。

政策由确定性代码判、写操作按事务设计这两条，项目做得比文档要求还严。
缺口集中在文档的第三、四、五条原则——**上下文数据层几乎不存在、成本引导只做了素材
没做呈现、事件驱动完全没有**；再加上文档点名的评测问题：现在所有指标都是对话质量
指标，一个业务指标都没有。

## 二、逐条对照

这里的"文档主张"指设计文档《二、核心设计原则》里的六条。

| 文档主张 | 项目现状 | 判断 |
|---|---|---|
| 1. 模型负责理解和编排，不负责决策 | `policy/engine.py` 做确定性判定；语言模型端口只做语义解释，解释时只能引用 `explanation_facts`；新的工具循环 `agent/tool_loop.py` 里模型拿不到没有政策标注的库存 | **已做到，且比文档更严** |
| 2. 写操作按事务来设计 | Booking Intent 幂等键、审批主题哈希（请求一变旧审批即失效）、乐观锁、原始响应写入不可覆盖存储、状态机没有绕过重验的直达边 | **已做到**，但 V1 没有真实写操作，"补偿逻辑"这条还没被真正考验过 |
| 3. 少问靠数据不靠模型 | 盘点时 `EmployeeProfileSnapshot`（员工档案快照）只有职级、部门、常驻城市、经理 4 个业务字段，没有任何偏好或历史。**2026-08-31 补上了 `services/travel_profile.py`**：从员工真的订过的行程里推出习惯，并带上"凭什么这么推"的理由。日历和 CRM 仍然零接入 | **本系统自己的数据已经用上；外部集成仍是缺口** |
| 4. 管控做成引导，而不是拦截 | 盘点时只有 `RuleEvidence`（单条规则的判定证据）和四档结论，差额、该谁批、换法建议都没有。**2026-08-31 补上了 `planning/cost_guidance.py`**，卡片上现在写"住宿超出差标 $520/晚，需 M2001 审批""换「综合推荐」出发时间不变，省 $200" | **已补上** |
| 5. 事件驱动，不只是问答 | 任务走到 `HANDED_OFF`（已交接）就终止。`outbox_events` 表（用来可靠投递通知的事务性外发表）已建好，但投递进程没写。没有航变监听 | **完全没有** |
| 6. 渐进授权 | 实际是"永远第 1 档"，靠 `providers/duffel.py` 里的开关实现，不是架构里的一等概念 | **只有最低档** |

设计文档《四、最容易被低估的三件事》里的第二件，单独列出来：

| 文档主张 | 项目现状 | 判断 |
|---|---|---|
| 评测不能只看对话质量 | 盘点时全部指标都在模型层：任务通过率、硬断言通过率、规则输出完整率、裁判打分（`evaluation_quality.py`）、工具调用效率（`evaluation_efficiency.py`）。**2026-08-31 补上了 `evaluation_business.py`**，现在有交接完成率、平均耗时、提前预订天数和超标发生率 | **已补上；缺真实数据的第一条基线** |

第一件（集成才是主要工程量）项目其实已经踩到并做得扎实：Duffel / LiteAPI / Mock / Replay
四个适配器、重验上下文存储、熔断、延迟重试、原文归档。缺的是**企业侧**集成——OA、
费控、审批系统、日历、HR，一个都还没有。

第三件（冷启动要设计）有个很好的底子但没补完：`planning/divergence.py` 的"按分歧提问"
（几种读法算出来的行程轮廓一样就不问）已经在减少无效提问，只是还没有组织级默认值可用。

## 三、改进方案

按性价比排序。每条给出为什么、落在哪个文件、怎么验收。

### P0 · 加一层业务指标评测　✅ 已完成（2026-08-31）

**为什么排第一。** 设计文档最尖锐的那句批评——"模型回答得像模像样但员工还是绕开去
用携程，说明产品是失败的"——项目此前完全无法自证。而这些数字从**已经存在的任务聚合
和审计轨迹**里就能算出来，不需要采集任何新数据。

已经落地的指标：

| 指标 | 数据来源 |
|---|---|
| 交接完成率（渠道内预订率的**上限估计**） | `HANDOFF_COMPLETED` 审计事件 |
| 平均耗时（任务开始 → 交接完成，墙上时间） | 审计事件时间戳 |
| 提前预订天数（交接时刻 → 首段实际出发） | 选中方案的 `TransportOffer.depart_at` |
| 超标发生率（选中口径 / 展示口径） | `PolicyDecision.evidence` 逐条读 |
| 例外审批率、平均澄清轮数、每任务工具调用数 | 任务聚合 |

**落点**：

- `services/evaluation_business.py` —— 计算与报告渲染，不调模型、不调供应商；
- `GET /metrics/business` —— 管理员可见的近期看板视图；
- `examples/measure_business_outcomes.py` —— 写进新报告目录，可读 PostgreSQL；
- `tests/test_evaluation_business.py` —— 端到端跑真链路 + 口径边界；
- `reports/evaluation-runs/business-outcomes-demo-20260831/` —— 演示数据的格式样例。

**一处原计划的更正。** 这份文档最初写的验收是"在 `reports/evaluation-runs/` 下已有的
历史运行上回算"，**这一条做不到**：历史报告存的是各 runner 自己的用例快照，里面没有
任务聚合，也没有审计事件时间戳。要有历史曲线，只能从现在开始按新格式积累，或者
另做一个把旧任务导出成聚合的工具。这里如实记下来，不含糊过去。

**还没做的**：真实数据上的第一条基线——需要先有一批真实任务。演示报告只用来验证
格式和口径，任何一个数都不能拿去下结论。

### P0 · 把成本摊到选择那一刻　✅ 已完成（2026-08-31）

设计文档第 4 条要的三件事，项目此前差的只是最后一步呈现。

1. **超标差额**。`RuleEvidence.actual` 和 `threshold` 是给人读的字符串，做不了减法。
   现在带数值阈值的规则（今天只有酒店夜费上限）额外给出 `actual_amount` /
   `threshold_amount` / `amount_currency`，差额由 `overage_amount` 算出来。
   **客户端不再需要 parse 展示文本**——那是错误的来源：措辞一改，数字就悄悄变了。
2. **该谁批**。审批人取员工快照上的直属经理，和真正创建 `ApprovalRequest` 时是
   同一个来源，所以卡片上写的人和后面真正收到审批的人不会是两个。
3. **权衡提示**。`planning/cost_guidance.py` 在**同一批已经摆出来的方案**里找更省的
   换法，不额外调供应商、不消耗那 12 次工具预算。省钱和代价（晚走多久、路上多久）
   放在同一个对象上，读的人拆不开——**只说省钱不说代价是诱导，不是引导**。

**落点**：

- `domain/models.py` —— `RuleEvidence` 的数值字段与 `overage_amount`；
- `policy/engine.py` —— 夜费上限规则填数值；
- `planning/cost_guidance.py` —— 溢价、超标明细、审批人、换法建议；
- `api/main.py` —— 每条方案带 `cost_guidance`（读时现算，不进持久化）；
- `frontend/src/utils/cost.ts` —— 数变成人话；`App.tsx` 卡片上多一行；
- `tests/test_cost_guidance.py` + `frontend/src/utils/cost.test.ts`。

真机跑出来长这样（Mock 库存，时钟冻在演示那天）：

```text
备选方案 · 需要审批
  住宿超出差标 $520/晚，需 M2001 审批
  换「综合推荐」出发时间不变，省 $200
```

**三条口径限制**：

1. **建议的上限就是这几条方案。** 因为不额外查库存，摆出来的方案里没有更便宜的，
   这里就一句建议都没有——那是真的没有，不是没算。
2. **不建议政策上更差的方案。** 更便宜但要多走一轮审批，那不是省，是麻烦。
3. **币种不一致时一句都不说。** 省的是 800 什么？说不出来就不凑。

这些全是加法，不动任何已编码不变量。

### P1 · 上下文数据层第一版　✅ 已完成（2026-08-31）

设计文档说"最大的精力应放在上下文数据层"，项目此前在这里投入为零。不做这层，
`planning/preferences.py` 里那七个软偏好只能来自用户当轮说的原话——一个每次都坐高铁
的人，第十次还是要再说一遍"优先高铁"，否则系统就把飞机排在前面。这正是文档警告的
"换了皮的搜索框"。

**已经落地的：**

1. `EmployeeTravelProfileSnapshot` —— 习惯偏好、常住酒店、成本中心，
   和 `PolicySnapshot` 一样是**带内容哈希的快照**，算出来就钉进任务；
2. `services/travel_profile.py` —— `TripHistoryPort` 加上读任务仓储的适配器，
   从**员工真的去订了的行程**里推习惯。这是唯一不依赖企业 IT 就能跑通的数据来源；
3. `PreferenceOrigin` 四档来源（说的 / 填的 / 推的 / 同事的），权重递减；
4. 冷启动：本人历史不足三趟时退到同职级同常驻城市同事，标记为 `ORG_DEFAULT`，
   权重最低的一档。

**不变量已经写死并配测试**（`ProfileStaysOutOfTheVerdictTests`）：同一批库存，
带不带画像，**候选池、每条方案的政策结论与证据、可行性判定必须逐字一致**，
只有排序分数可以变。画像一旦能碰这三样，它就成了绕过合规的后门。

**三条克制**（`services/travel_profile.py`）：

1. **少于三趟什么都不推断。** 一次是偶然、两次是巧合。
2. **达不到 70% 不算习惯。** 五段里三段坐高铁说明不了什么，那叫随机。
3. **每条推断都要能说出理由。** `evidence` 是一句给员工看的人话——
   「你最近 4 趟出行的 4 段里，有 4 段选了高铁」。说不出理由的推断不该存在。

**默认是关着的。** `trip_history` 不传就一个字都不变——接上画像那一刻排序分数就变了，
既有评测基线（`reports/evaluation-runs/`）和新数字不能放在同一张图上比。
要打开就传一个 `TripHistoryPort` 并新开报告目录重跑基线。

**两处原计划的更正：**

- **日历 / CRM 端口没有加。** 原计划写的是"先只抽端口不做实现"。做的时候发现这和
  仓库自己的规矩冲突——`planning/preferences.py` 开头那句"词表是承诺，承诺必须兑现"
  说的就是这件事：三个软偏好曾经有名字没实现，那个模块正是为了堵住它才存在的。
  加一对空端口是同一个毛病换个地方犯。真要接的时候再加，那时它才有实现。
- **组织默认值没有喂给 `planning/divergence.py`。** 原计划想用它少问一轮。写到这里
  才看清楚：那会撞上 `AGENTS.md` 的红线「模糊就问，不要猜」。
  **偏好可以推断，事实不能。** "他一般坐高铁"只改排序，猜错了顶多顺序不合心意；
  "他一般住一晚"是替他填了一个事实，猜错了就是照着错的东西去搜库存。
  这两件事外表像，性质完全不同——组织默认值只留在排序这一侧。

**没有的东西**：没有常旅客号（只在真正下单时有用，而这个系统不下单，现在存进来
只是白白多一块个人敏感数据）；没有偏好航司（`TransportOffer` 里根本没有承运人字段，
只有 `provider` 和 `ref_id`，那是供应商映射要先补的东西）。

### P1 · 把授权档位变成一等概念

现在"不自动下单"是靠 `providers/duffel.py` 和 `providers/liteapi.py` 里的开关实现的。
建议提升成企业级配置 `AutonomyPolicy`，和 `PolicySnapshot` 并列，四档写进枚举，
但**第 3、4 档在代码里显式抛"未实现"**。

三个好处，成本很低：

- 把"产品还没做"和"这家企业没授权"区分开——现在两者混在一起；
- 将来接真实预订时不用重写状态机；
- 审计里能记录"这一步是在哪个授权档位下发生的"。

**这不是放松 `AGENTS.md` 里的硬边界。** 硬边界保持不变，只是给它一个说得清楚的名字。

### P2 · 事件驱动

设计文档说"差旅的价值高地在变更而非首次预订"。这是现在和"能订票的聊天框"唯一真正
拉得开差距的地方，也是最贵的一块。

分两步，第一步是还债：

1. **先写完 Outbox 投递进程**。`outbox_events` 表和仓储在 PostgreSQL Phase D 就建好了，
   投递方一直没写，`docs/roadmap.md` 里挂了很久。审批通知是它的第一个用户。
2. **再引入 `TripWatch`**：交接完成后不结束，而是登记一个观察对象。外部事件（航变、
   日程变更）进来时，**关键约束是不能直接改老任务的状态，只能开一个新的改期任务**，
   复用现有全部规划、政策、审批链路，老任务的审计保持不可变。

这个设计和现有不变量完全兼容，也不需要动状态机。

### P2 · 政策规则扩维

设计文档说差标是"职级 × 城市 × 淡旺季 × 是否可向客户转嫁"。现在 `policy/engine.py`
只有 5 类规则：职级已知、币种、舱位席别、酒店城市上限、政策生效窗口。

建议至少补两条，因为它们正好对应文档提到的成本指标：

- `booking.advance_days`（提前预订天数）
- `hotel.city.seasonal_cap`（淡旺季上限）

`EnterpriseTravelPolicyConfig` 已经是严格 schema 化 + 历史快照固定的，加规则是**扩展
而不是改造**。按既有约定，配置升级必须追加新的政策快照，不能改写已有快照的内容。

### P2 · 把审批抽成端口

现在审批是内建的（`POST /approvals/{task_id}/decision`）。真实企业场景要路由到既有 OA
或费控系统。建议像供应商端口一样抽一个 `ApprovalPort`，现在的内建实现作为默认适配器。

现在做成本很低；等到有第一个真实客户再做，就要动一堆调用点。

## 四、有一条建议不照做

设计文档第 6 条把渐进授权画到了第 4 档"全流程托管"。建议**架构上留位置，但不把它
当作路线图目标**。

理由是文档自己那句话："真出一次重复扣款或者订错人，企业对整个产品的信任就没了。"
项目现在最值钱的资产恰恰是那套完整的证据链——快照哈希、审批失效、原始响应归档、
审计不可变。**全自动代订会先消耗掉这套资产建立的信任，然后才可能创造价值。**
在业务指标（P0 那套）能证明第 2 档已经跑顺之前，第 3、4 档不该排期。

## 五、下一步

P0 的业务指标层已完成，它是后面每一条改进的判断依据——加了偏好数据、加了成本提示
之后到底有没有变好，看这一层的数字。

接下来按顺序：

1. **攒出第一条真实基线，然后把画像这一层打开。** 三层代码都就位了，但还没有真实
   任务喂给它们。画像更是必须有真实历史才有意义——它现在是关着的，打开的前提是
   先有一条关着时的基线，否则没法说"打开之后到底好了没有"。
2. **P1 的另一条：把授权档位变成一等概念**（`AutonomyPolicy`）。成本低，
   而且能把"产品还没做"和"这家企业没授权"分开。
3. 之后进 P2：Outbox 投递进程 → `TripWatch` 事件驱动。

一条已经能看见的线：超标发生率、交接完成率这两个数，正好是成本引导和习惯画像
共同要改善的地方。等有了真实基线，这三件事可以放在同一张图上看。

## 六、2026-09-01 复盘：企业到底要什么、这份计划漏了什么、架构哪里有问题

复盘基准：分支 `semantic-entrypoint-and-judge`，提交 `91e860d` 之上的工作区；全量测试通过。
数字口径：`src/` 43,880 行，其中 `services/evaluation_*.py` 16,022 行（36%）、`agent/` 14,243 行
（32%）、`agent/orchestrator.py` 一个文件 4,509 行；`tests/` 21,501 行；`reports/evaluation-runs/`
下 163 个运行目录；`HANDOFF.md` 215KB、§1–§44。

### 6.0 先说结论

1. **系统在交接（handoff，把方案交给员工自己去官方平台下单）之后就结束了，从此什么都看不见**：
   不知道员工有没有真的订、订了多少钱、后来改没改。设计文档五个北极星指标里，渠道内预订率、
   提前预订天数、变更人工介入率三个在这个架构下**没有真值**，只能算代理值。第三节把
   "业务指标层"打了 ✅，但它量的是员工点了一下"我订好了"，不是订单。
2. **投入偏向评测，集成为零。** 评测代码 16k 行、意图相关 14k 行；企业侧集成（OA、费控、HR、
   日历）0 行；国内交通（高铁）0 行。设计文档《四》第一条"集成占人力三到五倍"，项目正在验证它的反面。
3. **架构上守边界的部分是范本级的，问题集中在四处**：没有"一趟差旅"实体、4.5k 行的编排器、
   四条并行的自然语言入口、领域模型新旧字段并存。都还没坏，都在拖慢每一次改动，都可以有计划地拆。

### 6.1 企业到底要什么——设计文档没说透的四点

设计文档《一、需求来源》写得对，这里只补它没说透的：

**买的人和用的人不是一个人，所以"少问"是存活条件不是体验优化。** 财务买的是管控和数据，员工
用的是省事。员工绕开去用携程，不是不守规矩，是官方渠道多花了他 20 分钟。项目已经理解这一点
（`planning/divergence.py` 按分歧提问、`services/travel_profile.py` 从历史推习惯），但数据源只有
本系统自己的历史。

**价值单位是"一趟差旅的生命周期"，不是"一次对话"。** 意图 → 方案 → 审批 → **下单 → 出行 →
变更 → 报销**。前四步只是把人送到门口；企业付钱买的是后四步产生的数据：真实花了多少、协议价
用了没有、退改损失多少、发票和行程能不能对上、人现在在哪（duty of care，企业对出差员工的安全
照护义务）。项目的领域模型里没有"一趟差旅"，只有"一个任务"（`TripTask`），任务到 `HANDED_OFF`
是终态，后四步在架构里没有位置。

**代订和团队出行是常态。** 行政助理替高管订、项目经理替五个人订同一趟。它改变三件事：谁的差标
（旅行者的）、谁的偏好（旅行者的）、谁来批（可能是旅行者的经理）。`TripRequestVersion` 只有一个
`traveler_id`，认证层绑定"任务的员工 == 登录员工"，没有"发起人 ≠ 旅行者"，也没有多旅行者。

**对中国企业，没有高铁库存等于没有产品。** 北京–上海、上海–杭州、广深这些高频线路高铁是默认
选项。现在接的是 Duffel（西方机票沙箱）和 LiteAPI（西方酒店沙箱），演示全用中文城市名，
`HANDOFF.md` §1.2 自己写着"上海→杭州改高铁 ❌ 没有铁路库存"。

### 6.2 对第三节改进方案的再评价

**做对的**：诚实（两处"原计划的更正"是主动推翻自己）；先有指标再判断别的改动；三条不变量
（画像只改排序、偏好可以推断事实不能、不排第 3/4 档授权）全部同意。

**不同意或没说透的**：

1. **P0 业务指标层的 ✅ 打早了。** `交接完成率` 来自 `HANDOFF_COMPLETED` 事件，而这个事件是
   员工点一下 `POST /trip-tasks/{id}/handoff-completed` 触发的——记录的是"员工说他去订了"。
   `提前预订天数` 用选中方案的出发时间，那是"计划"不是"预订"。四个指标两个没有真值。代码没错，
   缺的是**下单确认回流**（订单号回填，之后和费控对账），这才是让指标变真的那件事，而计划里
   没有一条提它。**顺带发现：前端根本没有"交接完成"按钮**——`App.tsx` 不调用
   `api.handoffCompleted`，也不显示 `booking_intent` 的跳转链接。这条指标从界面上连喂都喂不进去。
2. **计划继续在模型侧加码，集成侧仍然是零。** 第二节明说"企业侧集成一个都没有"，然后 P0/P1/P2
   六条里只有"审批抽端口"沾边。
3. **P1 画像层做完了，但是黑的。** `services/travel_profile.py` 345 行、测试齐全，但 `api/main.py`
   没传 `trip_history`——生产里它不存在。它需要"员工真的订过的行程"，而系统看不见下单，
   数据源天然残缺。顺序反了：先让系统看见真实下单，再推习惯。
4. **P2 事件驱动的依赖没写清楚。** "航变进来时开一个新的改期任务"——改期要知道**订了什么**
   （票号、退改规则、手续费），不是**计划了什么**。没有下单回流，`TripWatch` 只能从头重搜，
   那叫"重订"不叫"改签"。
5. **完全没提的**：发起人 ≠ 旅行者；团队出行；高铁库存；"一趟差旅"实体。
6. **P1 `AutonomyPolicy`**：便宜，但系统现在一个写操作都没有，这是给"什么都不做"贴标签。
   可以做，不该排在集成前面。

### 6.3 架构盘点

**好的地方**：`domain` 不依赖框架、数据库、供应商 SDK；端口/适配器用得一致；确定性边界比
设计文档更严；证据链完整（快照哈希、审批主题哈希、乐观锁、原文不可覆盖、审计不可变）；
评测协议的诚实规则（`null` 不填 0、Mock/真实分开报、硬失败不能被高分洗白）。

**有问题的地方**，按严重程度：

| # | 问题 | 证据 | 该怎么办 |
|---|---|---|---|
| 1 | **没有"差旅"实体，任务就是一切** | `TripTask`（`domain/models.py:700`）是聚合根，`HANDED_OFF` 无出边。交接后没有订单、出行、变更、报销 | 先加**下单确认记录**（本次落地，见 6.5）；等出现第二种任务（改期）时再抽 `Trip` 聚合——按仓库"没有实现的名字不该存在"的规矩，现在抽只会是空壳 |
| 2 | **`orchestrator.py` 4,509 行，一个类约 120 个方法** | 同时拥有四条入口、意图合并、澄清、搜索、规划、重验、审批、延迟重试调度、重启恢复、溯源、审计、追踪 | 按入口 × 生命周期阶段拆 |
| 3 | **四条自然语言入口并存，删除门槛定了没执行** | ADR-0002 定义了 legacy 的删除门槛；现在 semantic 也成了"给评测和回滚用"。每条入口在编排器、`api/main.py`、`frontend/src/api/client.ts`、评测 runner 各占一份；前端只用 `agentic` | 按 ADR 门槛删 legacy 和 semantic，D15 评测随之退役 |
| 4 | **状态机和产品入口形状不匹配** | `orchestrator.py` 工具循环处的注释："循环期间留在 DRAFT……现有状态机里没有一个格子正好对应这件事"；`_plan_from_tool_loop` 事后补 `SEARCHING → PLANNING → OPTIONS_READY` 只为让边合法 | 加 `AGENT_RUNNING` 状态，或给工具循环一个子状态机 |
| 5 | **领域模型新旧两套并存** | `TripRequestVersion` 同时有扁平 `origin/destination/...` 和 `journey`/`stays`、`hard_constraints` 和 `scoped_hard_constraints`；`TravelOptionVersion` 有 `legs`/`stays` 加 `outbound`/`inbound`/`hotel` 兼容属性。每处注释的理由都是"冻结评测数据" | `journey`/`stays` 做唯一真源，扁平字段改成只读派生属性，冻结集迁移一次。**评测集正在反过来约束领域模型** |
| 6 | **`TripTask.metadata` 成了杂物箱** | 编排器和 `api/main.py` 读写 64 个不同的键，存成 JSONB，schema、迁移、类型检查全看不见 | 至少把 `agentic_*` 一组提成带类型的子对象 |
| 7 | **建了没用的基础设施** | `outbox_events`：全仓库没有任何写入方，只有健康检查读计数；`travel_profile`：写了测了没接 | 要么接上，要么删掉 |
| 8 | **政策引擎相对其重要性投入最少** | `policy/engine.py` 289 行，5 类规则，只有夜费上限一条有数值阈值；夜费上限只有 10 座城市 | 财务真正关心的模块，该灌规则 |
| 9 | **供应商层缺国内交通** | `TransportMode.TRAIN` 有枚举，无任何铁路 provider | `composite.py` 有缝，挂一个只读铁路适配器 |
| 10 | 文档与前端形态 | `HANDOFF.md` 是会话日志不是交接文档；`App.tsx` 1,981 行单组件；163 个评测运行目录进仓库 | 不影响正确性，影响下一个人的启动成本 |

### 6.4 修订后的顺序

| 顺序 | 做什么 | 为什么排这 |
|---|---|---|
| 1 | **下单确认回流**（先做最简单的：员工回填订单号和实付金额；再接费控对账） | 没有它，P0 指标是代理值，P1 画像没数据源，P2 改签没地基 |
| 2 | 接一个**高铁只读库存** | 中国场景的准入门槛；`HANDOFF.md` §1.5 已列为待拍板 |
| 3 | 删 legacy 和 semantic 入口，编排器按阶段拆 | 每多留一天，每个新功能多写三份 |
| 4 | `ApprovalPort`（审批抽端口），然后接第一个真实 OA | 第三节里唯一的集成项，应该提前 |
| 5 | 政策规则扩维（预算、淡旺季、客户转嫁）+ 灌满城市上限 | 财务买单的核心 |
| 6 | 发起人 ≠ 旅行者 | 真实企业第一周就会撞到 |
| 7 | 画像层接通、Outbox 投递、`TripWatch` | 前面做完了它们才有意义 |
| — | **冻结评测代码，不再加新 runner** | 边际收益已经很低；现有门禁够用 |

### 6.5 第 1 项落地记录：下单确认回流（2026-09-01）　✅ 第一步已完成

**做了什么。** 交接之后系统第一次能看见"真的订了"：员工回填订单号和实付金额，任务从
`HANDED_OFF` 进入新的终态 `BOOKING_CONFIRMED`。业务指标层由此多了三个数，并把提前预订天数
的起点换成了员工说的下单时刻。

**落点**：

- `domain/enums.py` —— `TaskState.BOOKING_CONFIRMED`；`BookingConfirmationSource`，**只有
  `SELF_REPORTED` 一档**（费控对账接上时再加第二档，没有实现的名字不该存在）；
- `domain/models.py` —— `BookingConfirmation`（不可变）；`TripTask.booking_confirmation`、
  `confirmed_option()`、`booking_cost_variance()`——差额只有这一个算法，API 和指标都读它；
- `domain/validation.py` —— `validate_booking_confirmation_values`：只校验形状；
- `workflow/state_machine.py` —— `HANDED_OFF → BOOKING_CONFIRMED`，后者无出边；
- `agent/orchestrator.py` —— `confirm_booking()`：从 `READY_FOR_HANDOFF` 直接回填会先补记
  `HANDOFF_COMPLETED`；一个任务一条，第二次拒绝；
- `api/main.py` —— `POST /trip-tasks/{id}/booking-confirmation`；任务载荷多了
  `booking_confirmation`（含读时现算的 `planned_total` / `cost_variance`）；
- `services/evaluation_business.py` —— `booking_confirmation_rate`、
  `booking_confirmation_rate.of_handed_off`（说了"我去订了"的人里回来填单号的比例，
  1 减它就是交接完成率高估了多少）、`booked_cost_variance_ratio_mean`；
  `advance_days_reference` 新增 `booking_confirmation`；
- `services/travel_profile.py` —— 回填过的任务也算"真的订了"，证据更硬的排前面；
- 前端 —— **补上了此前根本不存在的交接面板**（`HandoffPanel`）：链接、"先记一笔我去订了"、
  回填表单、回填后的方案价/实付对照；`utils/booking.ts` 把差额写成人话，币种不同时明说
  "不比较"；任务列表多一格"已回填订单"；
- 测试 —— `tests/test_booking_confirmation.py`（流程 + 形状边界 15 条）；
  `test_evaluation_business.py` +4、`test_api.py` +1、`test_auth.py` +1（审批人 403、
  外人 404、本人 200、管理员遇已填 409）、`test_persistence.py` +1（SQLite 重启后 Decimal /
  来源 / 差额不丢）、`test_travel_profile.py` +1；`frontend/src/utils/booking.test.ts` 8 条。
  **全量：pytest 910 通过（此前 887）、ruff 全过、前端 build + test(47) + lint 全过。**

**三条口径限制，写在代码里也写在这里：**

1. **自述，不是回执。** 订单号系统核不了，金额系统核不了。指标名和报表标签都带着"自述"
   两个字；`booking_confirmation_rate` 比 `handoff_completion_rate` 硬的地方只有一个
   具体的号和一个具体的数，软的地方是没有核实。
2. **一个任务一条，写了不改。** 填错了开新任务。改一条已经进了指标的记录等于让历史曲线
   悄悄变形。
3. **币种不一致不换算。** 差额为 `None`，报表里记 `confirmation_currency_mismatch`；方案价
   和实付照给，读的人自己看得出两个币种不同。

**一处和 6.4 原文不同的决定。** 原文写的是"`Trip` 实体 + `BookingConfirmation`"。做的时候
按仓库自己的规矩（`planning/preferences.py`："词表是承诺，承诺必须兑现"）**没有抽 `Trip`
聚合**：现在一个任务对应一次交接、一条确认，`Trip` 抽出来只会是套在 `TripTask` 外面的
空壳，没有任何一处会读它。抽它的时机是出现第二种任务（改期）需要挂在同一趟差旅下的那天，
那时它才有内容。`BookingConfirmation` 是这一步真正承重的东西，它挂在产生交接的那个任务上，
将来 `Trip` 出现时引用它即可，不会返工。

**还没做的**：费控对账（第二档来源，把"自述"变成"核实过"）；把回填做进 IM/邮件提醒
（员工交接后三天没回填，主动问一句——这需要 Outbox 投递进程，见 6.4 第 7 项）；真实数据
上的第一条基线，现在所有数字都来自演示库存。

### 6.6 入口切换 · 第一步：CI 守产品入口（2026-09-01）　✅

**为什么先做这个而不是直接删旧入口。** 核对发现：旧入口被 5 个评测模块和 9 个 runner 调用，
而产品入口（工具循环）**没有任何离线替身**——CI 里的 540 条冻结用例走的全是产品已经不用的门。
删了旧入口，离线意图评测就悬空。所以顺序是：先让产品入口能离线跑，拿到并排数字，再定删除门槛。

**做了什么。**

- `agent/deterministic_tool_model.py`：工具循环的确定性替身，复用语义替身的解释器和编译器，
  第一轮发搜索、第二轮交付、搜空开口、越界打标；不重试、不换窗。
- `services/evaluation_dataset.py`：D1/D2 支持 `entrypoint="agentic"`；没有暴露面的指标记
  `not_applicable`（分类、缺失字段、越界标签、偏好），不记 0。
- `examples/run_product_entrypoint_evaluation.py` + `tests/test_product_entrypoint_evaluation.py`：
  D16 runner 与 CI 门禁；报告在 `reports/evaluation-runs/product-entrypoint-20260901/`。

**顺带修了三个产品缺口——它们是被替身第一次跑出来的：**

1. **循环写出来的请求一条要求都不带。** `_request_from_tool_loop` 没有 `hard_constraints /
   soft_preferences`：模型在提示词里被告知的两张词表根本没有出口，"只要直飞"到了规划器就没了。
   现在 `propose_options` 声明要求，规划器按它过滤排序；词表外的名字被拒绝。
2. **搜空之后是一轮澄清，不是"无可行方案"。** 真模型搜空会 `ask_traveler`，任务落
   `NEEDS_CLARIFICATION`、烧一轮澄清、前端显示"需要澄清"。现在落 `NO_FEASIBLE_OPTION`，
   原因和空搜的出处都留下。
3. **越界请求没有落点。** 工具循环没法说"这不是差旅"，只能问。现在 `ask_traveler(out_of_scope)`
   → `OUT_OF_SCOPE`，可重开、不占轮数。

**并排数字（D16，同一个解释器）：** D1 60/60；D2 澄清判断准确率 71.9% = 71.9%，
提前调供应商 0 = 0，编造库存 0 = 0。差异为零——正如它应该的：两个替身理解一样，只有架构不同。

**这一步没做的**：D4（agent-eval-v1）的 `model_mock` 模式、对抗集、旧的真实模型 runner 仍挂在
legacy 入口上；红队验收挂在 semantic 上。下一步逐个移植或退役，然后写 ADR-0003、删两条旧路。

### 6.7 入口切换 · 第二步：删掉两条旧路（2026-09-01）　✅

**做了什么。** ADR-0003：legacy 和 semantic 两条自然语言入口连同它们的编排器路径、agent 模块、
端口与适配器、API 路由、前端分支、旧的真实模型评测 harness（D9–D14 runner）、对抗集、语义红队
runner，以及只服务它们的示例和测试，全部删除。`IntentEntrypoint.LEGACY / SEMANTIC` 枚举值留着给
已持久化的旧任务读，这类任务可查看、不可续聊。

**数字。** 76 个文件、净减 26,885 行；`orchestrator.py` 4,685 → 2,880 行；测试 992 → 683
（少的都是被删代码的测试）；ruff、前端 build/test/lint 全过。删除门槛怎么满足的，

**删除付出的代价，也写清楚（ADR-0003 有完整表）：**

   单测，但"被污染的库存文本诱导模型"这类场景没有成套覆盖。第二个后续项。

**6.4 的顺序因此更新：** 第 3 项（删旧入口、拆编排器）的前半已完成；编排器还有 2,880 行，
拆法留给下一步。

### 6.8 定位决定与下一段计划（2026-09-01）

**项目所有者的决定：** 拿不到国内交通供应商的 API，也不需要上线。目标是**一个达到上线标准的
demo**：交通用国外库存（Duffel 机票 + LiteAPI 酒店），不做国内高铁；工程投入直接进"管控"和
"数据闭环"这两块。6.4 的第 2 项（接高铁）**取消**，不是推迟。

这改变了一个前提：国内差旅这一半系统永远做不了"帮你搜"。但企业买的是管控和数据闭环
（6.1），搜索只是留人的手段。demo 要证明的是后者。

**下一段按这个顺序做，每项一个提交：**
